## 直近の作業 (2026-09-20) — forgetful-tracker: 「毎日自動で鳴る」への作り替え

プラットフォーム全体の方向の話から、まず1本だけを試験台にして
「検索→使う→戻ってくる」の循環を成立させる、という方針にした。その1本が
forgetful-tracker。他の50本は「思い出して開く」必要があるが、これだけは
押し通知で向こうから届く。

見つかった根本問題は、**忘れっぽい人向けなのに思い出して操作することを
要求していた**こと。通知は一度鳴ると`notified`が立ち、手動で「次の外出のために
リセット」を押すまで二度と鳴らなかった。

- **通知の許可を聞くタイミングを後ろへ**。以前は何も登録していない画面の最上部に
  ボタンがあった。ブラウザは拒否を記憶するので、ここで断られると中心機能が永久に死ぬ。
  1件目を登録した直後に、「07:30にお知らせするには」と実際の時刻を入れて尋ねる形にした
- **毎日繰り返しをクライアントとサーバーの両方で**。`notified`(恒久フラグ)を廃止し、
  `lastNotifiedOn`(日付)と`checkedOn`(日付)に置き換えた。Edge Functionは送信後に
  `notify_at`を翻日へ進めて`notified`をfalseのままにするので、**アプリを二度と開かなくても
  通知が届き続ける**
- **「次の外出のためにリセット」と「終わったアイテムを削除」を廃止**。日付が変われば
  チェックは自動で外れる。代わりに任意の「チェックを全部外す」と、持ち物ごとの「休止/再開」を追加
- **使い方ガイドを追加**(イラスト付き3ステップ)。持ち物が0件なら開いた状態、
  1件でもあれば畳む。タイトルはベルが読み込み時に一度揺れ、下線は音が広がる弧にしてある
- 説明文(meta description / schema / subtitle)を、検索されそうな言い回しと
  「毎日繰り返す」実態に合わせて書き換え

テスト: `test/forgetful-tracker.test.js` を新設(30件)。時刻計算、繰り越し、
チェックの自動リセット、休止、旧データ移行を確かめる。**クライアントとサーバーの
次回時刻が一致すること**を、`index.ts`から実際の`nextOccurrence`を取り出して
突き合わせている(片方を直したときに落ちるように)。

実ブラウザで確認済み(エラーなし、追加→通知の尋ね方→チェック→休止/再開→
リロード復元、390px幅で横溢れなし)。

✅ **Edge Function はデプロイ済み (2026-09-20)**。
`supabase functions deploy forgetful-tracker-push --project-ref xyumhzecqhpzzzzylbwn` を実行し、
本番へ反映済み。毎日繰り返す通知が本番でも有効になっている。DBのスキーマ変更は無し。

既知の別問題(今回の変更とは無関係): `node test/run.js` で

## 直近の作業 (2026-09-18) — ecosystem-puzzle: タップと時間の分離（中心部の作り替え）

「タップのスピードと時間の経過は分離させないといけない」という指摘。前2回の修正
（猶予ターン拡張→取消、芽を食べ物に）はどちらも1タップ＝1ターンという前提の中での
調整で、その前提自体が問題だった。プレイヤーの唯一の行動が世界の時計そのものなので、
**急ぐという概念が存在しない**。

`state.turn` の使用箇所は5つだけだったので、分離自体は素直にできた。

- `takeTurn()` を2つに割った。`placeTile()` = プレイヤー（即座・無料・時計を進めない）、
  `worldTick()` = 世界（空腹・捕食・餓死・枯れ・石・季節・手札の補充）
- `state.turn` → `state.ticks`。1 tick = 旧1ターンなので、**既存の調整値は全部そのまま有効**
- 実時間の駆動は `setInterval`。`TICK_MS = 1800`。速度設定（Normal / Relaxed=2倍）を追加
- 手札はストック制（`HAND_MAX = 3`、`TICKS_PER_TILE = 1`）。長期の供給レートは旧版と同じ
  1枚/tick のまま、**貯めて一気に使える**ようにしたのが新しい自由度
- ガイドを開いている間・タブが裏にある間は時計を止める。**溜まった分の早送りはしない**
  （ポケットに入れて戻ったら全滅、を避ける）
- `sim.js` を全面的に書き直し。tick と placement を別々に回す本物のループになった。
  第3のbot `bankerBot`（手札を温存して危機に使う）を追加 — 分離で増えた手を測るため
- `rules.test.js` に「置いても世界の時計が進まない」ことを直接確かめるテストを10件追加（計50件）
- ガイドに「1b. The meadow moves on its own」を新設、旧「1ターン」表現を全部書き換え
- 実ブラウザで動作確認済み（3枚を4msで設置＝世界時間0、ガイド中の停止、速度切替、
  空手札、エラーなし）

計測（300回）: careful bot 中央値 7,600 / 餓死 0.8 per 100 ticks / 同時生存 3.32。
**banking bot 8,150 / 3.40** — 31%のtickで手札を温存しており、貯める判断が実際に効いている。
初心者bot 4,750。1プレイの長さ（約90 tick）と初心者との差は維持。

注: `HAND_MAX` のsweep（1,2,3,4,6）はほぼ差が出ない。即使いbotではcapが効かないため。
3という数字はbotで決めた値ではなく、「危機に応えられるが盤面を描き直せない」という判断。

## 直近の作業 (2026-09-17) — ecosystem-puzzle が「ゲームとして成り立っていない」件

前項の修正（猶予ターンを広げる）は**意味がなかったので取り消した**。時計はタップ数で
進むので、猶予を5ターンに広げても、その5ターンぶん盤面の全員が空腹になるだけ。
実測でも 3.7→3.4 餓死/100ターンとほぼ動かない。「速くタップしても餓死も速くなる」
というのが正しい指摘だった。

**本当の原因は「1食あたりのタップ単価」**。うさぎは9ターンごとに食事が必要で、
草1枚は芽3つ＝3タップ。つまり**うさぎ1匹がタップ予算の1/3を食う**。3匹で予算100%、
建設する余裕はゼロ、4匹は算術的に不可能。盤面が狭いのではなく、単価が高すぎた。

**修正：芽（sprout）も食べ物にした。** 救出の単価が3タップ→1タップになる。

- `apps/ecosystem-puzzle/script.js` — うさぎ `['grass','sprout']` / きつね
  `['rabbit','grass','sprout']`。**おおかみは据え置き**（頂点は事前に計画するもので、
  芽で救える頂点は頂点ではない）
- `MEAL_VALUE.sprout = 25` — 草は3タップで100＝33/タップ、芽は1タップで25。
  **慌てて芽を食わせる方が必ず損**になる価格にした。非常口であって戦略ではない
- `RABBIT/FOX/WOLF_STARVE_AT` を 11/16/21 に戻した（前項の13/19/25を取り消し）
- `nextGoal()` にうさぎの空腹ヒントを追加。空腹は梯子より優先して表示する
- `rules.test.js` — 「1タップで必ず救える」ことと価格の逆転防止を固定（計40件）
- 既存テスト「diets widen as the ladder climbs」が落ちたので、**数え方を
  『獲物の段数』に修正**。動物の段数は上ほど広がり、植物の非常口は上ほど狭まる、
  という別軸を1つの数に混ぜていたのが元の間違い。ゲーム側は曲げていない
- `RULES_VERSION` 5→6

## 2026-09-14 — Ecosystem Puzzle: 「餌を隠す」のが最適解になっていた

ユーザーが実際に遊んで2つ報告。1つ目「隣にうさぎを作ろうとしても前のうさぎが草を食べるので一生進まない」、
2つ目「うまく食べられないように草を配置しろってこと？」。2つ目が本質だった。

**1つ目への対応（不十分だった）** — 1ターンの処理順は 置く→マージ→空腹→捕食 なので、
**マージを完成させる最後の1枚は食べられない**。検証すると、空腹MAXのうさぎの真下に3枚目の草を置くと
草→うさぎ→(隣のうさぎと合体)→きつね まで1手で連鎖した。だが、これは仕様の説明であって修正ではない。

**2つ目＝本当の問題** — 食物連鎖を育てるゲームなのに、最適な打ち方が
**自分の動物から餌を隠すこと**になっていた。うさぎが得点源と妨害者を兼ねており、
空腹5/11で「食べられるから食べる」ため、貯めている草を常時つまみ食いする。

**修正: 動物は死にそうなときだけ食べる**

- うさぎ eat 5→**9**（starve 11）、きつね eat 7→**13**（starve 16）
- どちらも寿命の約82%地点＝**メーターが赤になる位置**。ルールが1つに揃った:
  「動物はバーが赤のときだけ、隣にあるものを食べる」
- 実測: うさぎの隣に草を置きっぱなしでも**8ターン残る**（以前は5ターン目に消えた）
- 警告リング `inReach()` は赤と同時に出るので必ず1ターン前に予告される
- `RULES_VERSION` 2→3（採点が変わるので古いベストは無効化）

**代償** — 捕食が唯一の得点源なので、スコア中央値は 900→700 に低下。
きつね到達率はむしろ微増（casual 83%）。最適解がトリックでないゲームと引き換えなら妥当と判断。

UI側は「1マス離して貯めろ」という回避策の案内をやめ、遊び方step3に
`An animal only eats once its bar is red.` を明記。盤面のオレンジ破線は
「空腹の動物が次のターンに届くマス」を示す（芽には付かない＝うさぎは草しか食べない）。

## 2026-09-14 — Ecosystem Puzzle をステージ制からハイスコア型に作り直し

ステージを追加するたびに仕様とバランス調整が発生して割に合わない、という判断で、

**ルール** — 5×5の盤面。空きマスをタップして手札を置くのが1ターン。

- 得点は**捕食のみ**。🐇が隣の🌿を食べて+30、🦊が🐇を食べて+150。同ターンにN匹食べれば×N
- 生きているタイルは全部同じカウンタを持つ。動物は餓死して🦴、植物は食べられないと枯れて🪴。どちらも盤面を塗りつぶす

- 空きマスがなくなったら終了。ハイスコアは `AppSync.store('ecosystem-puzzle','score')`

**なぜスイカゲームにならないか** — 頂点の🦊がゴールではないから。
🦊は最大の得点源だが、🐇を供給し続けないと餓死して骨になる。作るかどうかが毎回の賭けになる。

**`sim.js` を node のバランスハーネスにした** — `node sim.js` で script.js を直接驅動して何千回もボットに遊ばせる。
これが実際に2回助けている。

1. **最初のルールではゲームが終わらなかった** — マージは1手で盤面を2マス減らすので、
   普通に打つと盤面は永久に埋まらない（5000手打っても空き18マス）。
   → `STONE_EVERY` ターンごとに石が1つ浮き上がる外圧を追加し、2〜8 をスイープして **5** に決定
2. **🦊に到達できなかった** — 🐇×3 だと200戦中到達は最大4回。→ 🐇のみ **×2** にして約55%に

最終的な値で1500戦検証して、盤面の不整合・無限ループ・0点終了はゼロ。1戦は平均139手。

**はまったバグ** — `.modal { display: grid }` がブラウザ標準の `[hidden]` を上書きして、
遊び方モーダルが起動直後から開きっぱなしになっていた。`.modal[hidden] { display: none }` を明示して解決。

openStoreスタブ比較が改行コード(CRLF/LF)でずれているだけ。今回の変更とは無関係。

## 直近の作業 (2026-09-05) — Ecosystem Puzzle の面白さ改修 Step 1/3

ユーザーから「ひたすら草を植えるだけで楽しくない。連鎖のアイデア自体は良い」との指摘。
原因は **プレイヤーの判断が存在しないこと**(操作が1つだけ・植える位置に意味がない・
敗北条件がない・条件が全部「◯以上」)。全3ステップで「判断」を作る改修に着手。

**方針は「バランスの綱渡り」**(ユーザー選択):植えすぎ → 草が増えすぎ → ウサギ爆発 →
草全滅 → 全員餓死、という崩壊を実際に起こし、「今は植えない」を戦略にする。

### Step 1(完了) — 草の自然拡散 + 因果の可視化

- `CONFIG.grass.spreadMs`(7s)/ `crowdMax`(3): 生きた草が隣の空きマスに種を落とす。
  4近傍のうち3つ以上が埋まっていたら拡散しない(盤面が緑一色になるのを防ぐ「混み合い」ルール)。
  盤外も「埋まっている」扱い → 縁で自然に薄くなる
- 拡散は2フェーズ(収集 → 適用)。同じtick内で新しい苗がさらに拡散するのを防ぐため
- **これで連打が最適解でなくなった**(植えなくても草は増える → 待つ判断が生まれる)
- イベントログ(`#eventLog`): `🐰 ate 🌿` / `🦊 caught 🐰` / `💀 🐰 starved` / `appeared`。
  同じ内容は `×N` にまとめる。拡散はログに出さない(ログが埋まるため。canvasのエフェクトで表現)
- canvas のポップエフェクト(`state.pops` / `drawPops`): 食べた・狩った・餓死した瞬間に円が広がる
- チュートリアル `spread` を追加。How to play にも拡散の説明を1行追加

### Step 1.5(完了・2026-09-06) — 「きつねの捕食を黙って見ているしかない」問題

ユーザー指摘。調べたら**構造的にそうなっていた**: きつね550ms / ウサギ700ms でウサギの方が遅く、
狙われた時点で死が確定。しかもプレイヤーが触れるのは連鎖の一番下(草)だけで、
捕食の瞬間との距離が遠すぎた。方針は「操作は草のまま、草を誘導の道具にする」(ユーザー選択)。

- ウサギは**逃走時のみ高速**(`fleeMs` 320ms)。`fleeRadius` 4 で panic 開始
- `threatTo` にヒステリシス: panic は `fox.sightRadius + 1` まで解除しない。
  **ここは sightRadius と必ず連動させること** — 解除距離が視界より短いと永久に再補足されて逃げ切れない
- `refugeFor()`: 逃げ先は「近い草」ではなく「自分に近く、かつきつねから遠い草」。
  さらに到達時間比較(`toRabbit*fleeMs < fromFox*moveMs`)で先回りされる草を除外
- `flee()`: 壁ペナルティ必須。「きつねから離れる」だけだと**壁沿いに走って隅で詰んで死ぬ**
- 休憩を中断可能に: `headDownMs` 1.6秒だけ無防備、その後は接近で飛び起きる。
  (最初 `restSafeRadius` で「近くにきつねが居たら休まない」にしたら、
  ウサギが休まず草を食べ尽くして**生態系が全崩壊した**。休憩＝採食のブレーキだった)
- `nearestTarget`(採食): 草のみ対象＋きつねの近くの草を避ける。
  **苗を採食対象に含めてはいけない** — ウサギが新芽に張り付いて育つ端から食べ、
  草が拡散に必要な7秒を生きられず草原が枯れる
- `fox.sightRadius` 7 / `giveUpMs` 9秒 / `sulkMs` 6秒。**これが決定打だった**
- 表示: きつね→ウサギの赤い点線ロックオン + 警告リング、panic時は耳を寝かせて高速ホップ
- ログに `🐰 escaped 🦊` / `🦊 gave up the chase`

### 計測(すべて早送りシミュレーションで実測)

| 条件 | ウサギが死ぬ率(30秒・1対1) |
|---|---|
| 草なし | 100% |
| きつねの近くに草 | 3% |
| きつねから遠くに草 | 53% |

**giveUpMs 導入前は、どこに何を植てても 63〜82% で有意差なし**(＝プレイヤーの行動が無意味だった)。
きつねが諦めるようになって初めて、植える場所が生死を分けるようになった。

### 失敗した試み(戻した。再挑戦は非推奨)

- **茂み＝隠れ場所**(`inCover`: 周囲に草が2枚以上あるウサギはきつねから見えない)。

## 直近の作業 (2026-09-03時点・続き) — Bring List を本当の共有リストにした(SQL実行済み)

ユーザー指摘「バックグラウンド(Supabase)あるから共有できるんじゃない?」への対応。そのとおりだった。

### なぜ最初は「共有できない」と書いたか

同期に使う `user_app_data` の RLS が `owner_id = auth.uid()` で、**1人が自分の端末間で
同期する専用**だったため。他人の行は読めない。`family-schedule` のように専用テーブルを
作れば共有できる、というのが正しい答え。

### 選んだ方式: リンク共有型(ログイン不要)

飲み会の参加者全員に Google ログインを求めるのは現実的でないので、
**長いランダムURLを知っている人だけが読み書きできる**方式にした(ユーザーが選択)。

- `supabase/migrations/0034_bring_list.sql`(新規・**2026-09-03に実行済み**)
  - `bring_lists`(id, token, event) / `bring_list_items`(list_id, name, note, claimed_by, sort_key)
  - **ここが肝**: anon キーは公開キーなので `using (true)` で開けると
    **誰でも全リストを一覧できてしまい、参加者の名前が漏れる**。
    そこでリストごとの合言葉を**リクエストヘッダ `x-list-token`** で受け取り、
    `current_setting('request.headers')` と突き合わせて一致する行だけ許可している
  - 明細行のポリシーは `bring_list_allowed(list_id)`(security definer)経由。
    親テーブルのポリシーを二重評価しないため(0024 の再帰事故と同じ轍を踏まない)
  - 1リスト60件までのトリガー、文字数の CHECK 制約も入れてある
- アプリ側は**2モード**。描画は共通で、データの出し入れだけ差し替える
  - local … URLに合言葉なし。今までどおり `AppSync.store()`(ログイン不要・オフラインOK)
  - shared … `#l=<id>&k=<合言葉>` 付き。合言葉ヘッダを載せた専用クライアントで読み書きし、
    8秒ごと＋タブに戻ったときに取り直す(Realtime は anon＋ヘッダでは効かないので不採用)
- 取り合い対策: claim は `.is('claimed_by', null)` 付きで更新し、0件なら
  「Someone else just took that one.」と出す

- 見出しの色が変わる後半 → `<em>` を親の翻訳対象の中に置くのをやめ、**独立したキー**にした
- **アプリ数が入る文** → 言語によって数字の位置が違うので、`{count}` を含む1文を
  まるごと差し替える方式に変更。中にあった `<span id="lpCountInline">` は廃止
- `<br>` 2か所 → 削除して自然な折り返しに

数字入りの文は `data-i18n` が付かないので、**起動直後にも一度描き直している**
(通信を待つと英語のまま数秒出てしまうため)。0件のときはHTMLに書いてある数を使う。

(中国語は3文字で5px)。英語とスペイン語だけ偶然成立していた。
`white-space: nowrap` も `text-orientation: upright` も効かなかったので、
**縦書きをやめて右端の横書きピルに変更**。全言語で正しく測れる。

## 以前の作業 (2026-08-28時点) — アクセス解析を全ミニアプリにも入れた

「自分のアプリに何人来たか知りたい」という話から。Search Consoleは**検索経由の数字しか出ない**

スクロールすると、本文（カードや見出し）が画面下の固定タブバーの**上**に描かれてしまい、
タブバーが読めなくなっていた。

原因は重なり順。下タブバーは`<header>`の中にあるが、`body > header`と`body > main`は
どちらも`z-index: 1`で、値が同じときは**後ろに書かれている`main`が上**に描かれる。
`.site-nav`側の`z-index: 40`はheaderが作る重なりの箱の中だけの話なので効かなかった。
→ スマホ幅のときだけ`body > header { z-index: 40 }`にして解決。
モーダル（`.modal-scrim`は`z-index: 50`でbody直下）は、引き続きタブバーより前に出る。

**マイグレーション未実行でも壊れない**ようにしてある（テーブルが無ければアイデア0件扱い）。
ローカル(`python -m http.server`)で Requests / Matching 両方の表示を確認済み。
実際の投稿・削除の動作確認は、SQL実行後にログインした状態で行う必要がある。
